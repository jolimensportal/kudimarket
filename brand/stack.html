Everything above decides what to build.
None of it decides what to build it with.

Sixteen candidate systems checked against the project's own constraints, licences read from each repository's licence file and star counts and last-push dates read from the GitHub API on 7 Oct 2026. The marketplace-shaped platforms all fail on licence or staleness, which removes the obvious candidates. What survives is a choice between two application frameworks, and the deciding question is not the trader-facing app: it is which one builds a dispute, freeze and suspicious-report console fastest, on a licence that does not reach into our code.

The recommendation in five lines
The pickLaravel with Filament, on one PostgreSQL database. Filament is the strongest permissively-licensed operations console in open source, and this product's bottleneck is operations: disputes, freezes, suspicious-report queues, reconciliation, and a regulator's inspection.
The runner-upPayload 3, if staying in TypeScript matters more than console velocity. MIT, self-hostable, generated admin panel, PostgreSQL through Drizzle. Its admin is shaped like content management, so every dispute and AML queue is custom, and the framework is younger with a v2-to-v3 breaking-change history.
The market buildersAll three fail. Vendure core is GPLv3, Medusa's role-based access control sits behind a commercial licence, and Sharetribe is under a bespoke community licence that is not OSI open source and has not been pushed since May.
The cost of the pickThe TypeScript scaffold is replaced, and PHP joins the stack. The scaffold is small (one ledger package and twenty-one tests) and its arithmetic was already flagged as belonging outside application code, so little is lost. Crypto signing stays in a small separate service either way.
What it does not decideThe ledger, the chain, and the custody model. This page assumes PostgreSQL stays the system of record, which keeps the co-located-ledger option open. Choosing Formance later would split the database, and choosing a contract escrow would put on-chain state in front of both.

Criteria, in the order they bite

Derived from the product, not from taste
  • 1A licence that does not reach into our code. We intend to keep the product proprietary. Copyleft is not disqualifying in principle, but it converts every future hire and investor conversation into a licence question, so it costs real money in this market.
  • 2Self-hostable, with no mandatory managed tier. A regulated operator showing an inspector its trade ledger cannot depend on a vendor's hosted database for the record of truth.
  • 3An operations console, not just an API. Disputes, freezes, suspicious-transaction reporting, reconciliation and customer complaints are all queue-and-form work behind a login. That is the majority of internal tooling in this product.
  • 4PostgreSQL, because the ledger decision assumes it. Co-locating balances and trade state in one transaction is the cheapest way to remove the dual-write problem, and that option disappears if the framework only speaks to something else.
  • 5An append-only event log we control. Dispute evidence has to be hash-chainable and erasable on a schedule, which is a data-model choice, and the framework must not fight it.
  • 6Mobile-first on poor connections. Budget Android handsets, intermittent data, small bundles. An HTML-first or progressively enhanced front end beats a heavy client-rendered app.
  • 7Localisation, scoped to what we actually serve. English at launch, one locale. French only if the CFA corridor is admitted, Chinese only if RMB is admitted. Building three empty locale files is not localisation.
  • 8Queue and job infrastructure. Reconciliation, notifications, freeze timers and the twenty-four-hour reporting clock are all scheduled work, and they are table stakes rather than differentiators.

Why the operations console decides it

Read the harm catalogue in the fiat-leg document and count how much of it lands on a human behind a login: disputes, freeze handling and its appeal path, the tipping-off boundary, suspicious-transaction review, the twenty-four-hour reporting clock, reconciliation, complaints, and regulator inspection. That is the product's real internal surface, and it is a CRUD-plus-queue application, not a marketplace front end.

That is why the commerce platforms lose on their own terms. Their advantage is catalogue, cart and checkout, none of which we need: there is no basket, and the settlement is escrow. Their cost is an admin console that is either copyleft, enterprise-licensed, or content-shaped. Meanwhile the trade itself is the part every one of them leaves to us, because escrow, disputes and evidence rules do not exist as products to buy.

What the pick actually commits us to

If we take Laravel with Filament
  • →One database. PostgreSQL holds trades, escrow state, balances and the hash-chained event log, so the co-located ledger option stays open and the dual-write problem does not exist yet.
  • →Two deployment targets, not one. A Laravel application and console, plus a small crypto-signing service (TypeScript or Go) that holds keys behind a cloud KMS and answers release requests over an internal API. It is separated on purpose: it is the part that must survive a compromise of everything else.
  • →The trader front end is server-rendered and progressively enhanced. Listings, trade view, chat and dispute filing work as HTML over poor mobile data, with JavaScript as an enhancement rather than a requirement.
  • →One locale at launch: English, wired into the interface framework, so adding French or Chinese later is a translation file rather than an audit of the whole product.
  • →Queues do the waiting. Reconciliation, freeze timers, notifications and the reporting clock are jobs, not cron hacks.
  • →What we lose: the TypeScript scaffold and its tests, and a second language in the stack. Both are cheap now and expensive later, which is the argument for paying them now.

What happens next

  1. One week, one vertical slice, in the recommended stack: a trade that goes pending, a dispute that gets filed, an arbiter view that lists it, and a resolution that posts a hash-chained entry. The test is whether the console is faster to build than the same thing in Payload, not which one is nicer.
  2. Decide the chain and custody model first if the week is to be spent well: the signing service's interface depends on it, and the application asks for it in the same form.
  3. Keep the ledger question separate and later. PostgreSQL first, because co-location is the cheapest correct answer at our volume, with the spike tests named in the build-versus-adopt document.
  4. Do not buy a marketplace engine. Write down, before the slice starts, which parts of the vertical slice came from a library and which we wrote, so this page can be judged in six months rather than argued about now.
